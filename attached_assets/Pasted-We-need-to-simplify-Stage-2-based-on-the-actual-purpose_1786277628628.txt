We need to simplify Stage 2 based on the actual purpose of this application.

IMPORTANT:
Do NOT rebuild the application from scratch.
Do NOT modify the working Stage 1 authentication, company settings, branding, or audit foundation unnecessarily.

The application is NOT intended to be a full HR/employee management system.

The core purpose is:

Payroll Excel
→ Validate
→ Preview
→ Import payroll
→ Generate individual payslips
→ Create secure payslip links
→ Share via WhatsApp

==================================================
REMOVE EMPLOYEE MASTER DEPENDENCY
==================================================

The separate Employee Master module is NOT required.

Remove the Employee Master workflow from the application.

Do NOT require administrators to manually create employees before uploading payroll.

Do NOT require payroll Excel Employee IDs to already exist in an Employee Master table.

Do NOT block payroll import because an employee does not exist in a separate employee table.

The uploaded payroll Excel should be the source of employee/payroll information for each payroll run.

==================================================
WHAT TO DO WITH THE EXISTING EMPLOYEES MODULE
==================================================

Remove the "Employees" item from the main navigation.

Remove the Employee Master screens from the normal user workflow.

Do not delete historical payroll data that may already have been imported.

If the existing database contains an employees table that is no longer required, do not immediately drop it if doing so could affect existing data or migrations.

Instead:

- Remove its dependency from payroll import.
- Keep it temporarily if required for backward compatibility.
- Document that it is no longer used by the payroll workflow.

Clean up unused frontend components/routes where safe.

==================================================
NEW PAYROLL DATA MODEL
==================================================

A payroll record should belong directly to a Payroll Run.

Conceptually:

Payroll Run
    ↓
Payroll Records
    ├── Employee information
    └── Payroll information

Each payroll record should contain the employee information required for that payroll period.

At minimum:

- employee_id/code
- employee_name
- mobile_number
- email (if present)
- designation (if present)
- branch (if present)
- joining_date (if present)

and payroll fields such as:

- basic
- da
- hra
- other_earnings
- gross_salary
- pf
- esi
- tds
- other_deductions
- net_salary
- additional_components

The exact fields available will depend on the uploaded Excel.

Do NOT require all optional fields to exist.

==================================================

==================================================
EMPLOYEE ID
==================================================

Employee ID should still be strongly recommended because it is useful for identifying employees and historical records.

However:

- It does NOT need to exist in another table.
- Duplicate Employee IDs within the same payroll file should still be detected.
- A missing Employee ID should be a validation error if Employee ID is designated as a required column.
- Do not attempt to look up the employee in another database table.

The payroll record itself stores the Employee ID.

==================================================
MOBILE NUMBER
==================================================

Mobile number should be imported directly from the Excel if available.

This will later be used for WhatsApp delivery.

If mobile number is missing:

- Do NOT block payroll import.
- Show a WARNING.

Example:

"Mobile number is missing. WhatsApp delivery will not be available for this employee."

This employee must still be imported and their payslip must still be generated later.

VALIDATION
==================================================

Blocking errors:

- Invalid Excel file
- Required Employee ID column missing
- Required Employee Name column missing
- Blank Employee ID
- Blank Employee Name
- Duplicate Employee ID within the same payroll run
- Invalid numeric payroll values
- Required column mapping missing

Warnings:

- Mobile number missing
- Email missing
- Optional salary field missing
- Additional/unmapped columns present

Do NOT generate errors such as:

"Employee ID not found"

because there is no Employee Master lookup anymore.

IMPORTANT BUG FIX
==================================================

The current application has reported this runtime error:

"Cannot read properties of undefined (reading 'employeeId')"

Fix this as part of this refactoring.

The payroll workflow must never assume that an employee object exists in a separate Employee Master.

Remove any code that does something equivalent to:

employee.employeeId

when employee may be undefined.

Use the actual normalized payroll record instead.

For example, the payroll record's employee ID should come from the normalized imported Excel row.

All preview, validation and import code must safely handle missing values.

A missing Employee ID must produce a user-friendly validation error, not a JavaScript runtime exception.
